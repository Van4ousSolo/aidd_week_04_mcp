# Практика (Часть 2). Анализ генерации отчётов агентом и исследование траекторий

**Дата исследования:** 10 ноября 2026 года  
**Экспериментальный стенд:** локальное окружение Python с библиотекой `openpyxl`, REST API сервиса TODO (`http://127.0.0.1:5001`), агент Qwen Code с моделью `agentic/gc_v3`.

В базу задач было добавлено 30 синтетических задач командой `seed.py 30` поверх имеющегося пула; всего в тестовой выборке находилось 364 задачи:
- Выполнено: 118 задач
- В работе (не выполнено): 246 задач
- Из них просрочено (дедлайн строго раньше даты отчёта): 45 задач
- Распределение по приоритетам: high — 125, normal — 115, low — 124.

---

## 1. Постановка задачи и методология

Были проведены три независимые серии генерации отчёта агентом Qwen Code без предварительно подготовленного навыка (`skill`). Перед агентом ставилась цель:
- Получить данные по задачам исключительно через MCP-инструмент `list_tasks`.
- Сформировать двухстраничную аналитическую книгу Excel (`.xlsx`), включающую список задач и агрегированную сводку (статусы, приоритеты, процент выполнения, просрочка).
- Не устанавливать сторонние пакеты из внешней сети и не модифицировать записи в базе.

Траектории выполнения сессий протоколировались в файлы `trajectory.jsonl`, системный вывод перенаправлялся в `stderr.log`. Максимальный лимит времени на запуск составлял 480 секунд.

## 3. Детальный разбор поведения агента

### Сессия 1 (Каталог `reports/run1`)
Агент вызвал `mcp__todo__list_tasks`, успешно получил весь список задач, написал вспомогательный скрипт `build_report.py` на базе доступного интерпретатора Python с `openpyxl`. При первом запуске скрипта возникла ошибка формата из-за экранирования многострочного вывода, но агент оперативно модифицировал парсер и успешно сгенерировал файл `run1/report.xlsx`. Дополнительно сверил контрольные суммы через MCP и завершил работу.

### Сессия 2 (Каталог `reports/run2`)
Агент по собственной инициативе разбил выгрузку на части (лимит 100 записей), а затем запросил отдельно выполненные и невыполненные задачи. Часть записей агент попытался захардкодить вручную в тело генерируемого Python-скрипта. Это привело к рассинхронизации данных: при контрольной сверке было зафиксировано **14 несовпадений атрибутов** (включая неверные приоритеты и дедлайны). Попытки агента найти причину расхождений привели к циклическим исправлениям и превышению лимита времени (таймаут 480 с). Файл `run2/report.xlsx` непригоден для аналитики.

### Сессия 3 (Каталог `reports/run3`)
Агент сначала запросил данные с дефолтным лимитом 100, затем через `count_only=true` установил, что в системе 364 задачи, и повторно вызвал `list_tasks` с `limit=1000`. Написал полноценный скрипт `build_report.py`, рассчитал перекрестную матрицу распределения и сохранил валидный отчёт `run3/report.xlsx`.

## 5. Выводы и направления оптимизации

Генерация отчёта «с нуля» без использования навыков демонстрирует высокую нестабильность:
- Агент тратит от 130 до 480 секунд и сотни тысяч токенов на рутинное написание однотипного кода генерации Excel.
- Возникают ошибки парсинга больших объемов вывода в shell и опасные попытки ручной вставки данных в скрипты.
- Форматирование, структура листов и наименования колонок кардинально различаются от сессии к сессии.

**Решение проблемы:**
Вынесение логики построения отчёта в стандартизированный **навык (`skill`)** `make_report`. Скрипт навыка выполняет детерминированную обработку данных, гарантирует соблюдение единого формата, исключает галлюцинации LLM и сокращает расход токенов более чем в 5–10 раз.
