## 1. Спецификация формата отчёта (Часть 1.1)

Для решения задачи аналитики задач TODO была спроектирована специализированная двухстраничная аналитическая книга Excel (`.xlsx`), ориентированная на управленческий мониторинг выполнения задач и контроль дедлайнов.

### Лист 1: «Реестр задач»
Представляет собой детальный структурированный журнал всех существующих в системе задач, отсортированных по возрастанию `id`.
- **Колонки таблицы:**
  1. `ID` — уникальный числовой идентификатор задачи.
  2. `Название задачи` — текст заголовка задачи. В ячейках обязательно принудительно задается строковый тип (`data_type = 's'`) для предотвращения атак типа **Formula Injection** (CSV/Excel Injection), если задача начинается с `=`, `+`, `-` или `@`.
  3. `Приоритет` — русскоязычное отображение приоритета: `Высокий`, `Обычный`, `Низкий`.
  4. `Срок сдачи` — дата дедлайна в формате `YYYY-MM-DD` или статус `Без срока`.
  5. `Статус` — текстовый статус: `Выполнено` либо `В работе`.
  6. `Просрочена` — признак `Да`, `Нет` либо `—` (для задач без срока). Задача признается просроченной тогда и только тогда, когда она не выполнена (`done == false`), имеет установленный срок и этот срок строго меньше даты среза отчёта (`due < as_of_date`).
  7. `Дней до срока` — разность в днях между дедлайном и датой отчёта (`+N` дней до срока, `-N` дней просрочки).
- **Стилистическое оформление:**
  - Корпоративная шапка темно-синего цвета (`#1B365D`) с белым жирным текстом.
  - Закрепление первой строки (`freeze_panes = "A2"`) для удобства прокрутки.
  - Включенный автофильтр (`auto_filter`) по всем столбцам.
  - Чередование строк (зебра: белая и `#F7F9FB`).
  - Просроченные задачи подсвечены контрастным красным цветом.

### Лист 2: «Сводная аналитика»
Аналитический дашборд, агрегирующий ключевые показатели эффективности и распределение задач. Состоит из трех функциональных блоков:
1. **Блок ключевых показателей (KPI):**
   - *Дата отчёта* — контрольная дата анализа.
   - *Всего задач* — общее количество записей в базе ($N$).
   - *Выполнено* ($D$) и *В работе* ($P = N - D$).
   - *Процент выполнения* — отношение $\frac{D}{N} \times 100\%$ (округление до сотых).
   - *Просрочено* ($O$) — число активных задач с нарушенным сроком.
   - *Доля просрочки среди активных* — $\frac{O}{P} \times 100\%$.
2. **Матрица распределения (Приоритет × Статус):**
   - Таблица 3×4, детализирующая количество задач по уровням важности (`Высокий`, `Обычный`, `Низкий`) с разбивкой на выполненные, активные и просроченные, завершающаяся итоговой строкой суммирования (`ИТОГО`).
3. **Структура дедлайнов:**
   - Число задач с дедлайном и без срока, а также горящие задачи с дедлайном в пределах ближайших 7 дней.

## 2. Эксперименты без использования навыка (Часть 1.2)

В базу было загружено 464 задачи (после последовательного запуска `seed.py`). Агенту Qwen Code в чистых независимых сессиях подавалось подробное текстовое ТЗ с описанием вышеуказанного формата.

### Наблюдения по прогонам:
1. **Прогон 1 (Baseline 1):**
   - Агент обратился к MCP-серверу, запросил полный список задач через `list_tasks`, написал ad-hoc скрипт `build_report.py` на `openpyxl`.
   - В отчёт вошли все 464 задачи. Сверка с REST API подтвердила корректность подсчитанных итогов.
   - Однако агент потратил 11 шагов, свыше 290 000 токенов и порядка 2 минут времени только на первичное написание и отладку Python-кода.
2. **Прогон 2 (Baseline 2):**
   - Агент совершил типичную ошибку: вызвал `list_tasks` без явного указания `limit=1000` и получил стандартную порцию из **100 задач**, посчитав, что это вся база.
   - На основе 100 строк агент сгенерировал отчёт и отрапортовал об успешном завершении. В результате 364 задачи были потеряны, а сводная аналитика оказалась ложной (всего 100 задач вместо 464).
   - Кроме того, в визуальном оформлении наблюдался дрейф: названия листов и порядок колонок отличались от первого запуска.

**Вывод:** Без выделенного навыка результат недетерминирован. Модель может пропустить пагинацию/лимиты API, исказить расчет метрик или изменить структуру файла, несмотря на подробный промпт.

## 3. Разработка и тестирование навыка `make_report` (Часть 1.3)

Для устранения человеческого фактора и нестабильности LLM в каталог `practice/agent/.qwen/skills/make_report/` были вынесены:
1. **`TZ.md`:** подробное техническое задание со спецификацией API, валидации входных данных, защиты от Formula Injection и макета книги.
2. **`generate_report.py`:** эталонный скрипт генерации, реализующий детерминированный сбор данных из REST API, полную валидацию структуры задач, защиту от перезаписи существующих файлов (`FileExistsError`) и автоматическое форматирование Excel-книги.
3. **`test_generate_report.py`:** модульные тесты (`unittest`), проверяющие математику сводки, краевые условия (пустой список, дубликаты ID, некорректные даты), экранирование формул и защиту файлов.
4. **`SKILL.md`:** метаданные навыка с frontmatter (`name`, `description`) и сжатой инструкцией по запуску скрипта с параметрами CLI.

## 4. Эксперименты с подключенным навыком (Часть 1.4)

Агенту в новых сессиях подавалась предельно лаконичная пользовательская просьба:
> *«Сделай аналитический отчёт по задачам в Excel»* (без упоминания `make_report` и без спецификации колонок).

### Результаты:
- В обоих контрольных запусках (`skill1` и `skill2`) агент автоматически идентифицировал задачу и вызвал навык `make_report`.
- Вместо написания кода с нуля агент выполнил запуск:
  ```bash
  python .qwen/skills/make_report/generate_report.py --output report.xlsx
  ```
- **100% повторяемость:** оба сформированных файла имеют бит-в-бит идентичную структуру, полностью совпадающие цифры (все 464 задачи учтены без потерь) и эталонное визуальное оформление.
- Время выполнения сократилось до 15–20 секунд, а расход токенов уменьшился на 80–85%.

## 5. Исследование влияния `description` навыка (Часть 1.5)

Были протестированы три варианта параметра `description` в `SKILL.md`:

| Вариант описания | Текст `description` | Поведение агента на запрос «Сделай отчёт по задачам в Excel» |
|---|---|---|
| **1. Релевантное и четкое (Эталон)** | `Формирует структурированный аналитический Excel-отчёт (.xlsx) по задачам TODO с реестром задач, KPI, матрицей приоритетов и анализом дедлайнов. Применяй всегда, когда требуется составить отчёт, аналитику, выгрузку или сводку по задачам в формате Excel.` | **Skill успешно активирован во всех запусках.** Агент сразу обращается к скрипту навыка, отчёт строится за 1 шаг. |
| **2. Размытое / невнятное** | `Вспомогательный инструмент для работы с файлами данных, таблицами и системной информацией проекта.` | **Skill не активирован.** Агент проигнорировал `make_report`, счел его абстрактной утилитой и начал писать скрипт генерации с нуля через shell. В одном из прогонов попытался установить дополнительные библиотеки через pip. |
| **3. Нерелевантное (ерунда)** | `Утилита для архивации текстовых логов и проверки целостности сетевых пакетов.` | **Skill ни разу не выбран.** Семантическая близость запроса и описания нулевая; агент пошел по пути написания временных скриптов в каталоге сессии. |

**Вывод:** Поле `description` является ключевым семантическим триггером (router mechanism) для планировщика агента. При отсутствии явного ключевого соответствия между запросом пользователя и описанием навыка агент переходит к общему, неоптимальному циклу решения через написание кода с нуля.

## 7. Заключение

Перенос повторяющихся аналитических и расчетных задач из зоны свободной генерации LLM в детерминированные **Skills**:
1. Гарантирует надежность и бизнес-пригодность артефактов (исключаются пропуски данных, ошибки округления и галлюцинации).
2. Защищает конечные артефакты от уязвимостей (встроенный контроль Formula Injection в `openpyxl`).
3. Кардинально сокращает себестоимость и задержку работы агента (экономия вычислительных ресурсов и токенов контекста).
4. Требует точного составления семантического описания (`description`) для безошибочной маршрутизации запросов планировщиком модели.
